# Frightertainment private-preview launch readiness and security review
**Audited:** 10 October 2026. **Scope:** Current code plus read-only Cloudflare Pages and Zone security configuration. **Release status:** HOLD — do not make the site publicly accessible until all release gates pass.

## Security controls verified or implemented
- The public Pages build copies only an approved allowlist of files. The D1 Worker implementation, scripts, test fixtures, internal markdown, developer-only data, and provider credentials are excluded. Preview Pages are noindex and retain the existing Cloudflare Access gate.
- Static responses have a restrictive CSP (no unsafe-inline scripts, no unsafe-eval, allowlisted media frames), HSTS, frame protection, nosniff, limited browser capabilities, Cross-Origin-Opener-Policy and Cross-Origin-Resource-Policy. Dynamic JSON endpoints use restrictive response headers.
- User-supplied film and media text is escaped; trailer embed IDs are format checked and official-video matched; TMDB token is held server-side. Admin endpoints require the secret Bearer token, with bounded request bodies, strict input validation, no permissive cross-origin response headers.
- The contact form enforces same-origin/Cross-Site restrictions, bounded byte length (including chunked requests), strictly typed inputs, email-header control-character rejection, a honeypot, fixed sending recipient, and a fail-closed response when email delivery isn't configured.
- The **Cloudflare zone** has a dedicated, enabled WAF rate-limiting rule for POST `/api/contact`: block after more than 5 submissions per IP in 10 seconds (10-second mitigation). This affects the zone frightertainment.com and www, not *.pages.dev; the latter remain behind Access.
- CI runs dependency audit for high/critical advisories, unit tests, site/browser tests, Worker dry run, D1 local migrations, public/private build separation and link checks.

## Full Horror Vault integrity audit (10 October 2026)
The automated command `npm run audit:vault` inspects every source snapshot entry, title, year, QID, IMDb ID, internal detail route, canonical Wikidata source link, first-party source claim and permitted trailer metadata. It produces a per-film manifest and a summary in `audit-results/vault-audit.json` and `audit-results/vault-audit.md`, attached to every quality-workflow run. External HTTP reachability and verified TMDB/YouTube media availability remain separately identified as **unverified** unless actually tested. The historical data intentionally has no global poster or trailer fields: the live website retrieves rights-attributed TMDB media on demand for exact matches, preserving honest fallbacks when no media exists.

**Crawlers:** The licensed production TMDB cache has movie ID 1376400 with poster path `/lNXeEpg4yLSRwXwOeR5lbPgwbqL.jpg`; its source-checked VVS Films regional cinema listing remains `https://vvsfilms.com/anz/movie/crawlers/`. The site now pins that verified film ID for the selected editorial card and its upcoming-release row and includes it in the production artwork batch to prevent a missing/ambiguous poster lookup.

## Failed owner mobile contact test — 11 October 2026 (10:27 UK local)
An authenticated phone user submitted the contact form and saw the generic fallback ("The form could not send your message"). This proves the real browser-to-inbox delivery chain is NOT yet verified. Previous standalone Cloudflare Email Sending delivery evidence must **not** be described as a successful contact form test. Site remains private.

A targeted **review-only** fix:
- Renames the hidden `company` anti-spam field to nonsemantic `ft_trap_blank` to reduce the risk that mobile browser contact-detail autofill silently triggers a false bot rejection. The backend still recognises the old `company` key to catch bots; it never claims delivery for either filled honeypot.
- Makes the browser report non-sensitive failure references (`FT-AUTH-REDIRECT`, `FT-NONJSON-<status>`, `FT-HTTP-<status>`, `FT-MAILER-<status>`, `FT-MAILER-CONNECTION`, etc.), while keeping the unsent message and email-app fallback.
- The Pages endpoint now validates the mailer's JSON success acknowledgement rather than trusting HTTP 200 alone. It includes safe response codes for rejection or binding errors without exposing submitted names, emails or message text.
- Adds unit integration checks across the Pages handler and private mailer; Playwright covers mobile autofill, success/fallback and HTML interception.
- This does NOT establish that the issue was caused by autofill. It might instead be Access authentication, a binding error or upstream email failure. **A new authenticated real submission and inbox receipt are mandatory before launch.**
- Keep Cloudflare Access, production auto-deploy disabled and public launch on HOLD. Do not expose unrestricted diagnostic endpoints or contact contents in logs.

## Confirmed upstream mailer failure — owner test 11 October 2026, 11:16 BST (10:16 UTC)
The owner retried the updated Access-protected form on Android: subject "Test", message "Testing this". The UI displayed `Reference: FT-MAILER-503`. The Pages Function was invoked and called `CONTACT_DELIVERY`, which returned HTTP 503. This excludes missing browser validation as the immediate failure, but does not distinguish the mailer runtime's missing `EMAIL` binding from Cloudflare Email Sending rejection until the Worker returns an explicit cause. **PUBLIC LAUNCH REMAINS BLOCKED.**

Audit of earlier proof: the 03:59 UTC Cloudflare-sent email observed in Gmail was accepted through the **Email Sending REST API**, not the private Worker. That email did not validate the full browser → Pages → service binding → Worker → provider → Gmail chain.

Verified Cloudflare settings immediately following the failure: Worker script exists, private (no public Worker route), and its `EMAIL` send binding points to `Frightertainment@gmail.com`; account-level verified destination is `frightertainment@gmail.com` (lowercase). Email addresses generally compare case-insensitively, so a case mismatch is a **hypothesis, not a proven root cause**. The proposed review fixes recipient and binding configuration to exactly the verified lowercase address.

Code remediation in this private-review branch: verify Cloudflare EmailSendResult `messageId`, distinguish no EMAIL binding versus sender/recipient restrictions and provider failures via fixed FT-WORKER-* codes, and propagate only allowlisted codes from the private Worker through Pages. Never expose exception text or contact contents to visitors; Worker logs contain categories only. Test integration with fixtures, deploy the PRIVATE mailer separately (the Pages build does not deploy `worker/contact-mailer.js`), and inspect runtime telemetry. Re-test the owner's form and independently check Gmail receipt before closing launch gate.

**Neither passing GitHub tests nor successfully deploying the Worker constitutes proof of real email delivery.** Keep Cloudflare Access and production deployment restrictions unchanged.
